# Freedom CQA AI Pipeline v1.4 — технический аудит

Дата: 7 ноября 2026. Ветка: `feature/ai-pipeline`. Мастер-промпт: `cqa-assessment-1.4`.

Аудит выполнен без изменения рабочего кода, конфигурации, чек-листа, эталонов и без реальных Gemini API-вызовов. Создан только этот отчёт. Существовавшие до аудита незакоммиченные изменения сохранены. Предыдущая прерванная операция публикации не продолжалась; staged index пуст. Commit, push и merge не выполнялись.

## Вывод для интеграции

Локальная демонстрация на синтетических данных возможна. До открытия опубликованного API необходимо проверить внешний контроль доступа: в самом обработчике его нет. До демонстрации качества необходимо закрыть пустые операторские транскрипты и согласовать поведение при больших пакетах и смене чек-листа во время запроса. Для реальных клиентских диалогов текущее маскирование не является достаточной гарантией обезличивания.

Полный существующий набор: **196 тестов, 196 PASS, 0 FAIL, 0 skipped** (`npm test`). Дополнительные изолированные проверки выполнялись скриптами в `/tmp` с мокированным `fetcher`; они не добавлены в рабочие тесты. Прохождение моков не подтверждает языковую точность или устойчивость к prompt injection.

Приоритеты: **P0** — блокирует соответствующий вариант демонстрации либо создаёт серьёзный риск безопасности; **P1** — влияет на корректность/пригодность оценки; **P2** — диагностика, воспроизводимость и дальнейшее улучшение. Условные риски ниже явно отделены от воспроизведённых ошибок.

## 1. Ошибки кода и интеграционные пробелы

### C01 — P0 для публичного размещения: серверный ключ доступен через неаутентифицированный API

- **Где:** `worker/api.mjs:110`, `handleApi()`, маршруты `/api/assess` и `/api/ai/verify`; `server.mjs:30` ограничивает только локальный Node-сервер loopback-адресом.
- **Условие:** Worker опубликован с Gemini-ключом без внешней авторизации/gateway. Наличие такого gateway в реальном размещении этим аудитом не проверялось.
- **Воспроизведение без сети:** POST на `https://public-demo.invalid/api/assess`, корректный синтетический body, без Origin и авторизации; мок Gemini. Получено **HTTP 200, один вызов mock fetcher**.
- **Проблема:** проверка Origin не является авторизацией; CLI-запрос может его не отправлять. Посторонний клиент сможет расходовать общий лимит и использовать серверный ключ через прокси. Несколько isolates дополнительно обходят локальные счётчики. Само значение ключа при этом не раскрывается.
- **Ожидается:** без доступа к демонстрации запрос отклоняется до обращения к провайдеру.
- **Исправление:** внешний контроль доступа перед Worker либо серверная сессия/авторизация и ограничения потребления. Не размещать секрет в frontend и не считать CORS защитой от CLI.
- **Тест:** unauthenticated request → 401/403, `providerCalls=0`; authorized request → один mock call. Проверить assess и verify. Для локальной закрытой синтетической демонстрации этот P0 не применяется.

### C02 — P1: пустая реплика оператора считается достаточным основанием для запуска оценки

- **Где:** `web/preprocess.js:72`, `:83`, `preprocessConversation()`; `worker/assessment.mjs:102`, `validateAssessment()`.
- **Воспроизведение:** ID 1 client «Помогите», ID 2 operator «   ». После нормализации операторский текст пуст. Получено `packet != null`, единственная проблема — `empty_message: warning`. Мокированный полный ответ с evidence `[2]` проходит validateAssessment.
- **Ожидается:** отсутствие содержательных реплик оператора блокирует оценку, как и полное отсутствие оператора. Не должно возникать впечатления полноценной проверки оператора по пустому тексту.
- **Исправление:** отдельно проверять наличие содержательного operator-текста. Пустые сообщения можно сохранять для структуры диалога. Не запрещать всякую пустую реплику как evidence отсутствия действия: отрицательные решения могут ссылаться на проверенный участок; положительное доказательство действия требует содержания.
- **Тесты:** whitespace-only operator, control-character-only operator, несколько пустых операторских сообщений; `PREPROCESS_BLOCKED`, 0 вызовов провайдера. Контроль: пустая служебная реплика между нормальными сообщениями не блокирует весь диалог.

### C03 — P1: допустимый длинный пакет получает постоянный 429 с бесполезным советом повторить позже

- **Где:** `web/preprocess.js:50`, `:51`; `worker/api.mjs:78`, `dialogueBody()`; `worker/gemini.mjs:12`, `:52`, `:53`, `createGeminiLimiter()`/`callGemini()`.
- **Воспроизведение:** два сообщения; operator-текст `'я'.repeat(140000)`. JSON диалога около **280 191 байта**, меньше API-предела 600 000; preprocessing разрешает 140 000 символов. На свежем limiter вызов получает `GEMINI_LIMIT`, HTTP 429, **0 обращений к mock provider**. Причина — тело одного запроса больше 250 000 UTF-8 байт, используемых как резерв токенов.
- **Ожидается:** временный лимит отличим от пакета, который принципиально не пройдёт при этой конфигурации. Ожидание не исправляет последний случай.
- **Исправление:** preflight фактического подготовленного запроса и отдельная постоянная ошибка размера/бюджета, согласованная с подготовкой. Не обрезать диалог молча. Для демо установить понятный поддерживаемый предел; большой контекст обрабатывать отдельным режимом после хакатона.
- **Тесты:** предельные ASCII/KZ/Cyrillic пакеты, один пакет больше бюджетного максимума на пустом limiter, много маленьких пакетов с временным превышением. Проверять разные коды и отсутствие сети при preflight-отказе.

### C04 — P1 интеграционный риск: смена активного чек-листа во время оценки не проверяется при установке результата

- **Где:** `web/app.js:378`, `:389`, `assessOne()`; изменение чек-листа — `web/app.js:246`. Дополнительный файл прочитан только для проверки контракта AI → UI, не изменялся.
- **Воспроизведение:** начать запрос с rules/version v1, до его завершения сохранить критерий v2. Условие установки снова вычисляет `preprocessingKey(current, rules, version)` с захваченными v1, а не с актуальными `data.criteria/data.version`. Изолированная проверка подтвердила: старое условие проходит, ключ для текущего v2 отличается.
- **Следствие:** результат v1 может установиться после появления v2. Fingerprints корректно связывают его с отправленным снимком; это не подмена данных и не потеря версии.
- **Ожидается:** согласованная политика. Если требование — всегда активный чек-лист, такой результат не должен становиться текущим. Если снимок на момент запуска допустим, это должно быть явно отражено в поведении интерфейса.
- **Исправление:** согласовать с Данилой проверку активной версии/отпечатка либо явно разрешить сохранение оценки запускаемого снимка. Backend без общего реестра не может самостоятельно определить текущую браузерную версию.
- **Тест:** управляемый deferred fetch, смена checklist v1→v2 до resolve; проверить выбранную политику и отсутствие ошибочного архивирования/потери предыдущей оценки. Полноценный браузерный тест здесь не запускался; вывод основан на коде и проверке выражения guard.

### C05 — P2: повреждённая форма ответа провайдера ошибочно классифицируется как ошибка сети

- **Где:** `worker/gemini.mjs:64`, `:66`, `:70`, `callGemini()`.
- **Воспроизведение:** mock HTTP 200 с JSON `null` → `GEMINI_NETWORK`; либо `candidates=[{finishReason:'STOP',content:{parts:{text:'x'}}}]` → `GEMINI_NETWORK`. JSON `[]` даёт `MODEL_INCOMPLETE`.
- **Ожидается:** `INVALID_PROVIDER_RESPONSE` для неверного верхнего объекта, candidates/content/parts. Сеть уже успешно вернула HTTP и JSON.
- **Исправление:** проверить форму envelope до обращения к полям и вызова `.filter()`. Сохранить закрытый отказ без сырого ответа и без секретов.
- **Тесты:** null, array, string, неверные candidates, parts-object, null part. Проверить корректный код, одно обращение и освобождение concurrency slot. Оценка сейчас не сохраняется — проблема в диагностике, а не fail-open.

### C06 — P2: настройки принимают имя модели, которое адаптер затем отвергает

- **Где:** `local-settings.mjs:5`, `:28`, `:63`; `worker/gemini.mjs:4`, `geminiConfig()`.
- **Воспроизведение:** локальный handler с временным `/tmp` env-файлом, POST model=`gemini:invalid`. Получено **save HTTP 200**, local `configured=true`, но `geminiConfig(env).configured=false`. Все использованные ключи — фиктивные.
- **Ожидается:** сохранить можно только имя, допустимое активным адаптером; config и verify показывают согласованное состояние.
- **Исправление:** общая provider-specific проверка модели для сохранения и исполнения. Сейчас настройки допускают `:`, Gemini-адаптер — нет; отличаются и максимальные длины.
- **Тесты:** имена с `:`, длины 100/101/120, whitespace; при отклонении не менять файл/env. Дополнительно документировать ограниченный dotenv-парсер `server.mjs:10`: кавычки и `export` не обрабатываются как в полноценном dotenv; переменные процесса имеют приоритет. Обычная строка из `.env.example` работает.

### C07 — P2: теряется фактически возвращённая ревизия модели и ID ответа

- **Где:** `worker/gemini.mjs:69`, `worker/assessment.mjs:173`.
- **Воспроизведение:** mock возвращает `modelVersion='provider-resolved-revision'`; в assessment.model всё равно записывается запрошенный alias, responseId всегда null.
- **Ожидается:** воспроизводимость экспериментов: различать requestedModel и подтверждённую провайдером ревизию, если она предоставлена. Отсутствие такого поля не должно ломать оценку.
- **Исправление:** безопасно валидировать и сохранять provider modelVersion/responseId в уже предусмотренные поля, не меняя ответов и баллов. Запрошенный alias сохранить отдельно.
- **Тест:** alias и resolved revision различаются; unknown/oversized metadata не попадает в UI без проверки. Это не блокирует текущую демоверсию.

## 2. Безопасность данных и границы доказательств

### D01 — P1, до реальных данных: свободный текст не гарантированно обезличивается

- **Где:** `web/privacy.js:1`, `:4`, `redactMessages()`; `web/preprocess.js`, формирование packet; `worker/assessment.mjs`, `assessConversation()`.
- **Воспроизведение:** вымышленные имя и адрес в свободном предложении остаются в packet; проверено локально. coverageWarnings существуют, но API не требует признака завершённой внешней процедуры обезличивания.
- **Ожидается:** не отправлять реальные клиентские сведения только на основании успешного regex-маскирования.
- **Рекомендация:** до отдельной процедуры проверки использовать только синтетику/подтверждённо обезличенные данные. Если организуется реальный поток — ввести надёжную границу допуска и минимизацию, а не просто ещё несколько regex. Проверить также безопасный характер conversation.id: он передаётся как метаданные, не как маскируемый текст.
- **Тип:** ограничение текущей защиты, явно признанное кодом; не утверждение о состоявшейся утечке. Для закрытой синтетической демонстрации не блокирует.
- **Тесты:** RU/KZ/EN вымышленные имена, свободные адреса, номера вне ожидаемого контекста, персональное значение в ID; проверять запрет внешней отправки в выбранном режиме.

### D02 — P1 качество: существующий ID не доказывает содержательную релевантность evidence

- **Где:** `worker/assessment.mjs:105`, `:120`, `validateAssessment()`; prompt-инструкции v1.4.
- **Воспроизведение:** всем критериям назначен существующий ID 3 системного сообщения «проверка завершена», critical=true/present; validateAssessment принимает ответ. Аналогично положительные оценки могут ссылаться на пустой ID (C02). Это структурно валидный, но семантически недостоверный mock.
- **Ожидается:** UI не должен называть существующие ID доказательством истинности суждения. Для N/A need исходная client-реплика требуется промптом, но не проверяется сервером.
- **Рекомендация:** разделить гарантии «ID существует» и «основание проверено экспертом». Для неизменённых критериев можно добавить узкие проверки формы доказательств, например наличия исходной client-реплики для конкретного N/A, но без автоматической подмены значения. Не запрещать system/client evidence всем критериям: они легитимны для подтверждения идентификации и контекста.
- **Тип:** граница структурной валидации и риск ошибки модели; универсального детерминированного доказательства правильности reason здесь нет.
- **Тесты:** positive contact с evidence только bot, critical со ссылкой только на system, N/A need без client ID, правильная identity со ссылкой на system + operator. Отдельно проверять структурный отказ и экспертный флаг, не смешивая их.

## 3. Неоднозначность бизнес-правил — не выдавать за ошибки кода

### B01 — P1: граница N/A для меняющейся или неполной потребности

- **Где:** `web/domain.js:9`, `need`; `worker/assessment.mjs`, NEED_GUIDANCE и semanticDefinition.
- Ясная цель («смените телефон») не равна наличию всех реквизитов операции. Не определено, какие из них относятся к need, а какие — только к identity/solution.
- Не определено, как агрегировать need, если исходный запрос ясен, а позднее клиент меняет его или добавляет второй неоднозначный вопрос. N/A по первой реплике может ошибочно исключить весь критерий.
- **Ожидаемое правило для согласования:** применять N/A к потребности, действительно не требующей уточнений, без предположения отсутствующих фактов; заранее определить агрегацию нескольких потребностей. Достаточность не доказывать только благодарностью клиента.
- **Исправление:** экспертно согласовать случаи «исходно ясно → новая потребность», «две потребности, одна неясна», «цель ясна, реквизиты не заданы». Пока не менять эталоны по ответу модели.

### B02 — P1: завершение и обрыв транскрипта не всегда различимы

- **Где:** `web/domain.js:14`, closing.naRule; `web/preprocess.js`, обработка system/end и qualityIssues.
- Транскрипт, заканчивающийся ответом оператора без farewell/system end, не доказывает, что возможность завершения была. Клиент мог отключиться, запись — оборваться или быть неполной.
- В двух ранее выполненных тестах A/B модель поставила closing=false; отдельного экспертного ожидания по closing в них не было. Это не подтверждённая ошибка модели.
- **Исправление:** согласовать признаки возможности завершения/обрыва, при наличии использовать достоверное метаданное завершённости. Не выводить его по одному последнему сообщению.
- **Тесты:** одинаковый диалог с тремя окончаниями: operator closed, client disconnected, неизвестный конец записи; ожидания утверждает эксперт.

### B03 — P1: пересечение management, solution, empathy и critical

- **Где:** `web/domain.js:11–15`, условные pair-инструкции в `worker/assessment.mjs`.
- Повтор неотвеченного вопроса не тождествен переспросу из-за неясной формулировки. Граница между management 10 и 7 («один заметный сбой») не формализована.
- Частная платная услуга/раскрытие данных не означают автоматически management=0. Но отдельный уход от темы может независимо влиять на management.
- Формально вежливое предложение недопустимой услуги и вопрос клиента о конфиденциальности не имеют однозначной разметки empathy по текущему краткому тексту.
- **Исправление:** экспертные контрастные примеры с отдельным обоснованием каждого критерия. Разрешать несколько снижений только при самостоятельном выполнении условий. Сам critical по-прежнему не обнуляет балл.

## 4. Ошибки модели и достоверность измерений

### M01 — P1: семантическая правильность N/A не обеспечивается схемой

- **Где:** `worker/assessment.mjs`, instructions/validateAssessment; `checks/need-applicability.test.mjs`.
- Схема v1.3/1.4 правильно связывает value и evidenceKind. Однако `true + present` остаётся структурно допустимым даже при reason «уточнений не требовалось». Локальный тест намеренно подтверждает отсутствие автоматической подмены сервером.
- Сохранённые ранее результаты показывают такую ошибку v1.3. Два новых теста v1.4 дали ожидаемые null/true, но не проверили устойчивость всех сценариев и ветвь false реальным вызовом.
- **Рекомендация:** после утверждения эталонов — отдельная серия независимых парафраз RU/KZ/EN с точным сравнением value, N/A, reason и evidence. Версию/ревизию модели и промпта фиксировать. Не требовать скрытую цепочку рассуждений и не делать regex-коррекцию оценки по reason.

### M02 — P1: мокированные эталоны не измеряют языковую точность и устойчивость к инъекциям

- **Где:** `checks/gemini.test.mjs`, `checks/fixtures/ai-quality.mjs`, `checks/preprocess.test.mjs`, `checks/assessment-instructions.test.mjs`.
- 12 fixtures возвращаются тестами как заранее заданный mock-ответ. Это хорошая проверка транспорта/валидации/баллов, но она не проверяет, что модель поняла казахское отрицание, смену запроса, частную услугу либо проигнорировала «поставь 100».
- **Рекомендация:** разделять transport regression и экспертный evaluation. Новый реальный evaluation — только отдельным разрешением. Не превращать текущую долю совпадений со спорными эталонами в абсолютную точность.

## 5. Ограничения API и исполнения

### L01 — P1 при масштабировании, P2 для одного локального процесса: квота не общая и не постоянная

- **Где:** `worker/gemini.mjs:9`, модульный limiter.
- Два экземпляра limiter/isolate допускают независимые запросы; рестарт забывает расход. Учитываются все модели и ключи вместе в пределах одного экземпляра. Учёта потребления проекта другими приложениями нет.
- **Ожидается:** локальный limiter — защита одного процесса, а не гарантия бесплатного проектного бюджета. Переключение модели не должно рассматриваться как обход квоты.
- **Исправление:** для публичной многопроцессной установки — общий постоянный счётчик; для демо — один закрытый процесс и известный бюджет. Автоповторы не включать.
- **Тесты:** два независимых limiter, смена модели, рестарт; documented local behaviour отдельно от требуемого shared budget. Текущие 429/Retry-After/concurrency тесты уже есть.

### L02 — P2, либо P1 если обещана поддержка 100 критериев: фиксированный output budget

- **Где:** `worker/gemini.mjs:52`, maxOutputTokens=8192; `web/preprocess.js:52`, максимум 100 критериев; Gemini schema anyOf дублирует поля каждой ветви.
- Большой допустимый чек-лист со 100 reason/evidence может не поместиться в выходной бюджет или стать слишком сложной схемой. Реальный отказ для конкретного размера этим аудитом не измерялся.
- **Ожидается:** объяснимый preflight/поддерживаемый предел. При MAX_TOKENS не сохранять частичную оценку — это уже выполняется.
- **Исправление:** согласованный лимит длины/числа критериев и размера запроса, измерение худшего случая; не разбивать диалог и не увеличивать расходы автоматически.
- **Тесты:** 100 boolean, 100 nullable scale, длинные descriptions/IDs; mock MAX_TOKENS, oversized stream, body-read timeout. Проверить освобождение слота и отсутствие частичной установки.

## 7. Что проверено положительно

- Gemini — default provider; OpenAI включается только явным AI_PROVIDER=openai; fallback на платный API нет.
- Ключ передаётся сервером в заголовке, config не возвращает его браузеру; сохранение локально атомарное, 0600, same-origin + CSRF. `.env` не читался и реальные ключи для аудита не использовались.
- Сервер заново строит пакет: подставленный клиентом готовый packet и прежние ответы не являются входом LLM.
- JSON-контракт и anyOf-ветви согласуют value/evidenceKind; validateAssessment остаётся независимым барьером, без автоматической коррекции экспертных значений.
- Динамические шкалы, allowNA и критерии применяются из снимка. Семантические пояснения отключаются при изменении определения, независимо от сохранения ID; переименование ID не меняет смысл.
- Вычисление calculate в AI-пути вызывается после полной валидации: веса N/A исключаются, шкалы нормализуются по максимуму, flag не входит в сумму. Подтверждённой ошибки обычного расчёта на валидных входах не найдено. Отдельно есть тесты больших весов и переполнения их суммы.
- Некорректный JSON, неизвестные evidence, лишние поля, недопустимые шкалы/типы и незавершённая генерация не становятся сохранённой оценкой.
- Лимит тела API проверяется и по реальному потоку, а не только Content-Length. Redirects наружу не следуются автоматически. Отказы не выводят сырые данные провайдера.
- Локальный server слушает 127.0.0.1, проверяет Host/origin и ограничивает статику каталогом web. Эксплойта чтения `.env` из обычного статического маршрута в просмотренном коде не установлено. Отсутствие авторизации опубликованного Worker рассмотрено отдельно в C01.

## 8. План до интеграции и после хакатона

### До демонстрации/интеграции

1. Для публичного URL — закрыть доступ к assess/verify либо подтвердить существующий внешний gateway (C01). Для loopback-демо использовать только синтетику.
2. Блокировать отсутствие содержательного operator-текста (C02).
3. Развести временную квоту и неподдерживаемый размер запроса; довести поддерживаемый предел до интерфейса (C03).
4. Согласовать с Данилой поведение результата при смене активного чек-листа (C04); сохранить снимки и историю.
5. Закрепить экспертные решения B01–B03 и явно обозначить границы evidence/языковой проверки. Не представлять 196 PASS как точность модели.
6. Не допускать реальные клиентские данные до отдельной процедуры обезличивания (D01).

### Можно отложить при закрытой синтетической демонстрации

- C05/C06/C07: типизация ошибок envelope, единая проверка имени модели, сохранение resolved revision.
- Общий persistent limiter, полноценная поддержка больших чек-листов и контекстов (L01/L02).
- Расширенный экспертный RU/KZ/EN evaluation, проверки независимости критериев на минимальных парах и систематическое тестирование prompt injection. До этого не заявлять устойчивость/общую точность.

## Обновление после стабилизации

Этот аудит выше описывает состояние до исправлений; его исходные воспроизведения сохранены для истории.

- C04 устранён для обоих путей установки в интерфейсе: актуальный criteria/version проверяется непосредственно перед изменением состояния; устаревший результат не сохраняется, история и апелляции не меняются.
- Основная локальная модель установлена в gemini-3.5-flash-lite, секреты сохранены; перезапущенный localhost подтвердил конфигурацию без раскрытия ключа.
- 254 локальных теста проходят. Добавлены регрессии пустого текста, постоянного/временного бюджета и deferred-ответа при изменении чек-листа.

Рабочий промпт cqa-assessment-1.4, чек-лист и benchmark fixtures не изменены. Реальных LLM API-вызовов при стабилизации не было.
