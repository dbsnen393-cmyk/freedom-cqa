# Freedom CQA — AI BRO

Система команды **AI BRO** для контроля качества клиентских диалогов Freedom Broker. Оценивает работу оператора по восьми критериям, показывает основания в транскрипте, поддерживает пересмотр оценок и формирует результаты для сдачи на хакатон.

Веб-интерфейс предназначен для работы проверяющего. Командные скрипты получают наборы и выполняют пакетную оценку с сохранением прогресса. Прототип не является официальным продуктом Freedom.

## Быстрый запуск

Используйте **Node.js 22 или новее**. Внешние npm-зависимости не требуются; устанавливать пакеты перед запуском не нужно. Скрипты загрузки и оценки используют встроенный `process.loadEnvFile`.

1. Откройте терминал в корне репозитория.
2. Скопируйте `.env.example` в `.env` и заполните подключение к источнику и выбранному провайдеру.
3. Запустите сервер:

```sh
node server.mjs
```

Откройте [локальный интерфейс](http://127.0.0.1:4173). Сервер слушает только локальный адрес; порт по умолчанию — `4173`.

Пример структуры `.env` без секретов:

```dotenv
ORGANIZER_API_URL=
AI_PROVIDER=gemini

GEMINI_API_KEY=
GEMINI_MODEL=gemini-3.5-flash-lite

GROQ_API_KEY=
GROQ_MODEL=openai/gpt-oss-120b

OPENAI_API_KEY=
OPENAI_MODEL=gpt-5.4
```

`ORGANIZER_API_URL` получите у организаторов. Значение `AI_PROVIDER` выбирает `gemini`, `groq` или `openai`; заполните ключ соответствующего провайдера. Имена моделей выше — настройки по умолчанию, а в итоговый файл попадает фактически использованная модель из ответа API. После ручного изменения `.env` перезапустите сервер.

В локальном интерфейсе подключение к модели также можно настроить через верхнюю панель. Ключ сохраняется на стороне сервера и не возвращается браузеру. `.env` исключён из Git; исходные ссылки с подписью доступа и ключи нельзя помещать в исходники или результаты сдачи.

## Для проверяющих

В публичном репозитории есть серверные API-маршруты, скрипты и `.env.example`. Ключи провайдера и ссылка доступа к источнику в Git не публикуются. Файл `AI_BRO_judges.env` команда передаёт проверяющим **отдельно по закрытому каналу**; он не входит в репозиторий.

После установки Node.js 22 или новее выполните в PowerShell:

```powershell
git clone https://github.com/dbsnen393-cmyk/freedom-cqa.git
cd freedom-cqa
Copy-Item -LiteralPath 'C:\path\to\AI_BRO_judges.env' -Destination '.env'
node server.mjs
```

Замените путь в `Copy-Item` на расположение отдельно полученного файла. Затем откройте [локальный интерфейс](http://127.0.0.1:4173). Сервер использует `.env` для подключения к данным организаторов и модели; содержимое файла не требуется вставлять в браузер.

Вместо переданного файла можно скопировать `.env.example` в `.env` и указать собственный ключ выбранного провайдера и доступ к источнику организаторов. Реальная оценка расходует квоту соответствующего аккаунта. Сохраните файл настроек приватным: не добавляйте его в Git, публичные вложения или журнал проверки. Срок действия доступа зависит от организаторов и владельца ключа.

## Работа в интерфейсе

1. Загрузите `DEV` или выберите другой доступный источник в верхней панели. Для уже загруженного DEV кнопка «Открыть DEV» переключает набор без повторного запроса; «Обновить набор» запрашивает свежие данные.
2. Найдите диалог по поиску, языку, каналу или статусу. «Подготовить набор» проверяет данные и формирует пакет без обращения к модели.
3. Откройте диалог и нажмите «Оценить через ИИ». Сервер заново подготавливает полный транскрипт, маскирует распознаваемые персональные значения и проверяет структурированный ответ модели.
4. Проверьте значения, основания и начисленные баллы каждого критерия. Кнопки с номерами реплик открывают соответствующие фрагменты.
5. Для пересмотра нажмите «Оспорить» у критерия. В разделе «Апелляции» проверяющий сохраняет итоговое значение и основание решения. Баллы пересчитываются; исходная оценка и история сохраняются. Повторная оценка архивирует прежние апелляции.

Апелляции относятся к критериям. Отдельных апелляций на сообщения нет. Обновление источника с изменённым транскриптом делает прежнюю оценку неактуальной и сохраняет её в истории.

### Звонки и переписка

В звонке кнопка таймкода с наушниками запускает выбранный фрагмент записи. Нажатие на текст или метку дорожки выбирает реплику и перемещает позицию, но само не запускает остановленное аудио. Доступны скорость воспроизведения, перемотка и следование за репликами. В переписке аудио нет: кнопка запуска включает автопрокрутку.

Метки обозначают начало реплик. Исходные данные не содержат точных окончаний речи или разметки по словам. Если таймкод находится на конце или за концом записи, плеер останавливается и показывает предупреждение с длительностью файла. Длина аудио не используется для автоматического исправления таймкодов.

В настройках синхронизации можно вручную задать сдвиг и исключение системных пауз записи. Положительный сдвиг означает, что аудио начинается позже транскрипта. Исключайте паузы только после проверки конкретной записи. Сервис не определяет автоматически длительность речи, тишину и перебивания.

## Получение наборов через CLI

Все команды ниже запускаются из корня репозитория. Исходные наборы сохраняйте вне него: они содержат транскрипты и могут содержать служебные ссылки на записи.

```sh
node scripts/fetch-datasets.mjs --group DEV --output ../data/DEV.json
node scripts/fetch-datasets.mjs --group FBroker --output ../data/FBroker.json
node scripts/fetch-datasets.mjs --group Swap --output ../data/Swap.json
```

Имена групп чувствительны к регистру при загрузке:

- `DEV` — набор разработки: по заданию 60 чатов и 5 звонков.
- `FBroker` — контрольный набор из ровно 10 диалогов; скрипт проверяет количество и уникальность исходных ID.
- `Swap` — только загрузка. Скрипт пакетной оценки запрещает SWAP как по аргументу группы, так и по метке внутри файла; регистр этого запрета не меняет.

Загрузка не вызывает модель. Скрипт сообщает группу, количество записей и результат сохранения, не печатая ключи или ссылки доступа.

## Пакетная оценка и возобновление

Обязательные аргументы `scripts/assess-dataset.mjs`: `--input`, `--group`, `--team`, `--output`, `--cache-dir`. Для оценки разрешены только `DEV` и `FBroker`.

Сначала выполните проверку контрольного набора без запросов к модели:

```sh
node scripts/assess-dataset.mjs --input ../data/FBroker.json --group FBroker --team "AI BRO" --output results/prod/results.json --cache-dir ../data/cqa-cache/prod --dry-run
```

`--dry-run` проверяет подготовку и пригодность существующего кэша. Он не вызывает API модели и не записывает кэш или итоговый файл, но требует настроенного провайдера.

Команды реальной оценки:

```sh
node scripts/assess-dataset.mjs --input ../data/DEV.json --group DEV --team "AI BRO" --output results/dev/results.json --cache-dir ../data/cqa-cache/dev
node scripts/assess-dataset.mjs --input ../data/FBroker.json --group FBroker --team "AI BRO" --output results/prod/results.json --cache-dir ../data/cqa-cache/prod
```

Эти команды отправляют подготовленные диалоги выбранному провайдеру и расходуют его квоту. Перед запросами скрипт проверяет все входные записи. Запросы выполняются последовательно; между их началами выдерживается не менее 13 секунд. Для предусмотренных временных ошибок разрешён один повтор после паузы 65 секунд. Ошибки доступа, ключа, модели и другие критические сбои останавливают новые запросы; оставшиеся записи отражаются как ошибки.

После прерывания повторите ту же команду с тем же `--cache-dir`. Успешный результат используется повторно только при совпадении исходного текста, чек-листа, провайдера, модели и версии промпта. Устаревший кэш не подменяет новый запуск. Каталог кэша обязательно должен находиться **вне репозитория** — скрипт проверяет это.

Совпадающие сохранённые ошибки по умолчанию не запускаются повторно. После устранения причины добавьте `--retry-errors`:

```sh
node scripts/assess-dataset.mjs --input ../data/FBroker.json --group FBroker --team "AI BRO" --output results/prod/results.json --cache-dir ../data/cqa-cache/prod --retry-errors
```

Кэш записывается после обработки каждого диалога; итоговый JSON — после завершения прохода и проверки формата. В консоли выводятся JSON-строки прогресса. Завершение с `status: "complete"` и кодом `0` означает успешный проход. `complete-with-errors` или код `1` требуют проверки: файл может содержать явные ошибки обработки, которые нельзя считать готовыми оценками.

## Результаты для сдачи: JSON 1.0

Официальные файлы размещаются в корне репозитория по следующим путям:

```text
results/
  dev/results.json
  prod/results.json
```

Их создаёт пакетный скрипт через `web/submission.js` по официальному приложению «Как сдать результаты». В каждом файле один объект с `schema_version: "1.0"`, `team_name: "AI BRO"`, `model` и массивом `results`. Режим модели — `external_api`; при использовании нескольких моделей перечисляются их фактические названия.

Каждый исходный `conversation_id` должен встретиться ровно один раз. Для `status: "ok"` нужны все восемь критериев:

| `criterion_id` | Допустимое `value` | Вес |
|---|---|---:|
| `contact` | `true`, `false` | 10 |
| `discovery` | `true`, `false`, `null` | 15 |
| `identification` | `true`, `false`, `null` | 20 |
| `consultation` | `0`, `5`, `10`, `15`, `20`, `null` | 20 |
| `empathy` | `true`, `false` | 15 |
| `dialogue` | `0`, `4`, `7`, `10` | 15 |
| `closure` | `true`, `false`, `null` | 5 |
| `critical` | `true`, `false` | Без баллов |

У каждого критерия есть краткое `rationale` и `evidence_turns`. Номера доказательств — позиции с 1 в **исходном массиве транскрипта**, включая клиента, бота и системные события. Только реплики оператора отдельно не перенумеровываются.

`score.final_score` вычисляется кодом по официальным весам и округляется до двух знаков. Например, `dialogue = 7` при весе 15 даёт 10,5 балла до нормирования. При `null` вес критерия исключается, оставшиеся веса нормируются к 100. `score.critical_flag` совпадает с `critical.value` и не обнуляет итог.

Неудавшийся диалог сохраняется в файле со своим ID, пустым `criteria`, `score: null` и коротким `error`. Ошибка не подменяется нулевой оценкой. Экспортёр проверяет IDs, типы, шкалы, индексы доказательств и итоговую арифметику; для PROD дополнительно проверяются ровно 10 записей, включая ошибки. Исходные транскрипты, аудиоссылки и ключи в официальный результат не включаются.

Перед сдачей проверьте оба файла и включите их в commit и push открытого репозитория, переданного организаторам, до стоп-кода. Локально созданный файл или commit без push не завершает сдачу.

## Где хранятся данные

Веб-интерфейс хранит диалоги, оценки, апелляции и эталоны в `localStorage` конкретного браузера. Общей базы между пользователями нет. Кнопка «Экспорт» в списке диалогов создаёт резервную выгрузку веб-приложения; это отдельный формат, не официальный `results.json`.

CLI использует исходный JSON и свой файловый кэш вне репозитория. Он не читает `localStorage`, не переносит автоматически браузерные апелляции и не меняет состояние интерфейса. Для официальной пакетной сдачи используйте команды выше.

Ключи и подключение к источнику остаются на сервере. Перед отправкой модели распознаваемые персональные данные маскируются; это не гарантия полного обезличивания свободного текста. В запрос не входят прежние оценки, апелляции и служебные аудиоссылки. Подробности конвейера: [AI_PIPELINE.md](AI_PIPELINE.md).

## Проверки и ограничения

```sh
npm test
node build.mjs
```

Тесты проверяют подготовку, валидацию ответов, формулы, апелляции, историю, таймлайн, аудио, CLI и официальный экспорт с синтетическими данными и подменёнными ответами. Они не измеряют точность модели на контрольном наборе. Сборка создаёт серверный артефакт в `dist/`; публикация выполняется отдельно.

Для ручного сравнения с независимыми эталонами сохранена служебная страница `/#validation`. Она скрыта из основного меню. Учебные копии `TEST` позволяют проверить оценку, апелляцию и пересчёт без вызова модели; демонстрационные и учебные значения не являются результатами оценки качества реальных диалогов.

Общая точность на Ground Truth не заявляется без отдельной проверки на независимой разметке. Корректный JSON, пройденные тесты и завершённый запуск сами по себе не доказывают правильность оценок.

## Основные файлы

- `web/` — интерфейс, расчёт баллов, подготовка, апелляции и воспроизведение.
- `web/submission.js` — официальный экспорт и строгая проверка JSON 1.0.
- `worker/assessment.mjs` — инструкции модели и проверка её ответа.
- `worker/gemini.mjs`, `worker/groq.mjs`, `worker/provider-config.mjs` — подключение провайдеров; OpenAI обрабатывается в `assessment.mjs`.
- `worker/api.mjs` — источник диалогов и аудиопрокси с HTTP Range.
- `scripts/fetch-datasets.mjs` — загрузка исходных наборов.
- `scripts/assess-dataset.mjs` — пакетная оценка, возобновление и сдаваемый JSON.
- `server.mjs` — локальный сервер; `build.mjs` — сборка.
- `checks/` — автоматические проверки.
